# Requirements: LXR sound module on RP2350 (Waveshare RP2350-Zero)

## Introduction

The repository at `/home/chris/Projects/lxr-desktop-app` is the LXR V2 desktop drum machine firmware for an STM32F765 (Cortex-M7, 216 MHz, hardware double-precision-capable FPU, I2S codec CS4344, SD card, LCD, buttons, encoders, step sequencer, DIN and USB MIDI). This feature turns it into a **headless-capable drum sound module** for RP2350 boards, by default the Waveshare RP2350-Zero, with the Raspberry Pi Pico 2 also supported (RP2350, dual Cortex-M33 at up to 150 MHz, single-precision FPU, 520 KB SRAM, external QSPI flash). The module is played from MIDI. It has no step sequencer. The user interface is a separate layer that talks to the sound engine through a defined interface, so the engine runs identically with any UI or none. The first release has no front-panel hardware: sounds are edited over MIDI and a serial console. An encoder-and-OLED panel is a planned later iteration (see Requirement 7).

## Glossary

- **Engine**: the DSP and voice code (drum voices, snare, hi-hat, cymbal, mixer, FX bus, parameter array, preset data) with no knowledge of any display, button, knob or LED.
- **Module**: the complete RP2350 firmware image.
- **Engine API**: the C header interface that is the only way the UI layer and the MIDI layer read or change Engine state.
- **UI layer**: all code that reads physical controls or drives displays and LEDs, plus its mapping onto Engine API calls.
- **Voice**: one of the six existing drum voices (three drum voices, snare, hi-hat, cymbal).
- **Block**: one audio processing unit of `OUTPUT_DMA_SIZE` stereo frames.

## Requirements

### Requirement 1: Build and run on the RP2350

**User story:** As the builder, I want the firmware to build for the RP2350-Zero (and the Pico 2) so that I can run the drum engine on that board.

#### Acceptance criteria
1. WHEN `cmake --preset release` and `cmake --build --preset release` are run with the Pico SDK and an arm-none-eabi toolchain on PATH, THEN the build SHALL produce a `.uf2` and an `.elf` for board `waveshare_rp2350_zero` by default, and for `pico2` with `-DPICO_BOARD=pico2`, with no STM32 HAL, CMSIS-STM32 or STM32 startup/linker file in the link.
2. WHEN the `.uf2` is copied to the board in BOOTSEL mode, THEN the Module SHALL boot and be ready to play within 2 seconds of power-up.
3. The Module SHALL run on a stock RP2350-Zero or Pico 2 board with no hardware beyond what Requirements 3, 4 and 7 list.
4. The repo SHALL target the RP2350 only. All STM32 sources and files (`Drivers/`, `Middlewares/`, `FATFS/`, `USB_DEVICE_MIDI/`, `STM32F765VGTX_FLASH.ld`, STM32 startup and HAL-MSP code, bootloader-image tooling) SHALL be removed from the build and from the tree. Git history keeps the STM32 version.
5. The GPL-3.0 licence headers and `NOTICE.md` terms SHALL be preserved on all carried-over files.

### Requirement 2: Sequencer removal

**User story:** As the builder, I want the sequencer gone so the Module is only a sound source and fits the smaller CPU and RAM budget.

#### Acceptance criteria
1. The Module SHALL NOT contain the step sequencer, Euclid generator, clock-sync/tempo code, pattern/sequence storage, or any UI for them.
2. The Module SHALL NOT ship MIDI clock, start/stop or song-position handling beyond ignoring those messages safely.
3. WHEN MIDI clock, start, stop or continue messages arrive, THEN the Module SHALL ignore them without glitches or stuck voices.
4. Preset data SHALL contain only sound parameters (voices, mixer, FX, MIDI channel/note mapping). Pattern data in imported presets SHALL be skipped, not misread.
5. Parameters whose only purpose was sequencing (tempo, swing, step/track selection, mutes tied to the sequencer) SHALL be removed from the Engine API.
6. Voice-level modulation that the sequencer drove per step (for example per-step velocity or per-step parameter locks) SHALL be dropped, while the velocity-to-parameter modulation driven by incoming MIDI velocity SHALL stay.

### Requirement 3: Audio output

**User story:** As the player, I want clean stereo audio out of the Module.

#### Acceptance criteria
1. The Module SHALL output stereo audio at 44.1 kHz or 48 kHz (one rate, fixed at build time) with 16-bit or better resolution.
2. WHILE all six Voices and the full FX bus are active, THE audio output SHALL have no buffer underruns for 10 minutes of continuous MIDI retriggering at the maximum supported rate.
3. The Module SHALL provide a Block-based render path where one Block is rendered per DMA/PIO half-buffer completion.
4. The audio output SHALL be I2S, generated by a PIO program, driving a PCM5102A DAC module (pins BCK, LRCK, DIN, with the board's SCK tied low so the PCM5102A generates its own master clock). The I2S GPIOs SHALL be listed in the pin table in `design.md`.
5. The Module SHALL report the worst-case Block render time over a rolling window through the Engine API, so CPU headroom can be verified on hardware.

### Requirement 4: MIDI input

**User story:** As the player, I want to trigger and edit sounds from MIDI.

#### Acceptance criteria
1. The Module SHALL accept MIDI only as serial MIDI 1.0 on a 3.5 mm TRS jack (MIDI Association CA-033 Type A: ring = current source, tip = current sink): 31250 baud, 8N1, on a UART RX pin, through an opto-isolated input circuit (H11L1, or an equivalent such as a 6N138, per the MIDI 1.0 electrical spec).
2. The Module SHALL NOT include USB MIDI. The USB port SHALL be used for power, for flashing (BOOTSEL mass storage and picotool reset-to-BOOTSEL) and for the serial console (USB CDC, Requirement 7.2).
3. WHEN a Note On for a mapped note arrives on a Voice's MIDI channel, THEN the Voice SHALL trigger with the note velocity applied as in the current firmware.
4. WHEN a Control Change or NRPN that the current firmware accepts for sound parameters arrives, THEN the matching Engine parameter SHALL change with the same value scaling as today.
5. The Module SHALL keep the existing parameter CC/NRPN map so existing controller templates keep working, minus removed sequencer parameters.
6. Note-to-trigger latency from MIDI byte received to first audio sample in the output buffer SHALL be at most 2 Blocks.
7. IF the UART receive buffer overflows or a framing error occurs, THEN the Module SHALL discard the partial message, resynchronise on the next status byte, and count the error in a counter readable through the Engine API.

### Requirement 5: Engine ported to RP2350 compute limits

**User story:** As the builder, I want the DSP to fit the RP2350 so that the sound stays recognisably LXR.

#### Acceptance criteria
1. The Engine SHALL use single-precision `float` and integer math only. No double-precision operation SHALL execute in the audio path.
2. The Engine SHALL fit in the RP2350's 520 KB SRAM including FX delay/reverb buffers, with a linker map report committed to the repo showing the margin.
3. IF the render budget is missed at 150 MHz, THEN the system clock SHALL be raised first, in steps, to at most 250 MHz and 1.20 V core voltage, keeping the lowest clock that passes the load, soak and temperature checks. IF the budget is still missed, THEN a Voice or FX reduction or a core split SHALL be documented in `design.md` before it ships. A reduction (for example fewer reverb taps, lower FX buffer lengths, or fewer simultaneous FX) and a core split SHALL each be approved by the user before it ships.
4. The built-in sample data (`Samples.c`, about 200 KB of source) SHALL be stored in flash and read in place, not copied to RAM.
5. A host-side test build of the Engine (compiled for the development machine, no hardware) SHALL render a fixed MIDI script to a WAV file, and the Pico build SHALL be checked against the same script for equal output within a tolerance stated in `design.md`.
6. The user-sample SD-card memory feature SHALL be removed unless the user decides to keep it (decision recorded in `design.md`).

### Requirement 6: UI abstracted from the Engine

**User story:** As the builder, I want the UI to be swappable so I can try minimal hardware without touching DSP code.

#### Acceptance criteria
1. Engine source files SHALL NOT include any LCD, button, encoder, LED, ADC-pot or menu header, and SHALL NOT call any function defined in the UI layer.
2. The Engine SHALL expose a single Engine API header covering: trigger a Voice with velocity, get/set a parameter by ID, enumerate parameters with name, range, default and unit, load/save/select a preset, read output level and CPU load, and subscribe to a "parameter changed" callback.
3. The UI layer SHALL depend on the Engine API only. A build with the UI layer removed SHALL still compile, boot and play from MIDI.
4. WHEN a parameter changes from MIDI, THEN the UI layer SHALL be notified through the callback so any display reflects it, with no polling of Engine internals.
5. Parameter metadata (names, ranges, display text such as the current `Cc2Text.c` and `MenuText.h` content) SHALL live in a table the UI reads through the Engine API, not inside the menu code.
6. The Engine and the Engine API SHALL be buildable and testable in the host test build of Requirement 5.5 with a stub UI.
7. The UI layer SHALL be organised so that a second UI (for example a second display or a control surface on spare GPIOs) can be added by implementing only the UI layer interface.
8. The monolithic `menu.c`, `buttonHandler.c`, `ledHandler.c`, `lcd.c` and `frontPanelParser.c` code (about 9,000 lines) SHALL NOT be ported as is. Only what the chosen minimal UI needs SHALL be rewritten against the Engine API.

### Requirement 7: Minimal UI: no hardware UI plus a serial console

**User story:** As the builder, I want the module to need no front-panel parts for now, with a text console for editing and testing, so the engine/UI split is proven before any panel hardware is chosen.

#### Acceptance criteria
1. The first release SHALL have **no front-panel UI hardware**. The Module SHALL be fully playable and have every sound parameter edited over serial MIDI CC/NRPN.
2. The Module SHALL provide a **serial console UI** on the board's USB port as a USB CDC serial device, usable with any serial terminal on the host computer and needing no extra hardware.
3. The console SHALL support these commands: `help`, `params [voice]` (list names, ranges, current values), `get <param>`, `set <param> <value>`, `trigger <voice> [velocity]`, `preset load <n>`, `preset save <n>`, `preset list`, `status` (CPU load, worst Block time, MIDI error counter, underrun count).
4. Each console command SHALL call only the Engine API. IF a parameter name or value is invalid, THEN the console SHALL print an error naming the problem and change nothing.
5. WHEN a parameter changes from MIDI, THEN an enabled `watch` command SHALL print the change from the Engine API callback.
6. The console SHALL run in the host test build on stdin/stdout, so the same commands drive the host Engine.
7. The console SHALL run at lower priority than audio and MIDI. Console input or output SHALL NOT cause audio underruns or dropped MIDI bytes.
8. The UI layer interface (Requirement 6) SHALL allow a later encoder-and-OLED UI to be added without changes to the Engine or the console. That UI is **not built in this spec**.

### Requirement 8: Preset storage

**User story:** As the player, I want sounds to persist across power cycles.

#### Acceptance criteria
1. The Module SHALL store presets in on-board flash (a reserved sector range at the end of the board's 4 MB flash), not on an SD card, unless the user decides otherwise.
2. WHEN a preset is saved, THEN the audio output SHALL NOT glitch. Flash writes SHALL be performed so the audio path keeps running (for example by running audio from RAM during erase/program, or by deferring writes to a quiet moment).
3. WHEN the Module powers up, THEN it SHALL load the last saved preset or a factory default if flash is blank or corrupt (CRC mismatch).
4. The Module SHALL provide at least 16 preset slots.

## Out of scope

- Any sequencing, pattern, song or arpeggiator feature.
- A new sound-design feature or new Voice type.
- The LXR V2 bootloader and `.img` update flow.
- An encoder-and-OLED or knob front panel (later iteration).
- Polished enclosure, PCB design and front-panel artwork.
- Wireless (Pico 2 W) features.
- Driving the RP2350-Zero's WS2812 RGB LED.
